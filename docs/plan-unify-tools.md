# Plan: hợp nhất tool dựng sẵn và tool thư viện

Nguồn: `docs/plan-v10.md` (Backlog "mọi tool đều có profile"), `docs/ux-capabilities.md`. Người dùng đã chọn hướng A (hợp nhất) ngày 2026-11-06.

## Vấn đề

Hai loại tool tách nhau: tool dựng sẵn (`catalog.json` → `ToolDef`, `Workspace.Bindings`) có bảng hậu tố và profile; tool thư viện (`ToolEntry`, `Workspace.LibraryBindings`) thì không. `AddToolWindow` chỉ liệt kê bốn kind của catalog và không giống `ToolEditWindow` của thư viện.

## Thiết kế chốt (các phase sau coi đây là hợp đồng)

1. **Một thực thể tool = `ToolEntry`** (tools.json). Mọi tool có thể có bảng hậu tố, action, profile, stack.
2. `ToolEntry.BaseCommand`: `Command` nếu có lệnh, ngược lại đường dẫn file chạy đặt trong ngoặc kép. Tool lệnh có `Path` rỗng thì chạy tại thư mục workspace (bỏ ràng buộc "phải có đường dẫn").
3. `ToolEntry.SuffixSource` (tuỳ chọn, JSON `suffixSource`, EmitDefaultValue=false): `{ file, jsonPath | pattern | values, template }`, template có `{id}`. Thay cho `actionsFrom` cứng của npm; cấu hình được cho bất kỳ tool nào.
4. **`ToolCatalog` giữ tên và chữ ký công khai** (`All`, `Find(kind)`, `ActionsFor`, `FindAction`, `FromSubcommand`, `ReadSource`, `OptionsFor`) nhưng nay tra tool trong thư viện: `kind` = `ToolEntry.Id`. Có seam cho test (`ToolCatalog.Source`, mặc định đọc `ToolStore.DefaultPath`, cache theo stamp file). `ToolDef.From(ToolEntry)` dựng view trong bộ nhớ.
5. **Phần đọc `catalog.json` tách sang `ToolPresets`** (file giữ tên `catalog.json`, schemaVersion 4). Preset chỉ dùng để: (a) nhận diện thư mục (`Detect`), (b) sinh `ToolEntry` mẫu khi người dùng chọn gợi ý, (c) migration. Không còn là loại tool riêng.
6. `ToolBinding`: `Kind` đổi tên thành `ToolId` (JSON vẫn `"kind"`), thêm `Args` (JSON `"args"`, EmitDefaultValue=false). `Cwd` là ghi đè theo workspace. Thư mục chạy thật = `binding.Cwd` (nếu có) → `tool.Path` (tool lệnh có path) → gốc workspace; tool file chạy giữ hành vi `CommandBuilder.LibraryCwd` hiện tại.
7. **`LibraryBindings` bị gộp vào `Bindings`**. Property `LibraryBindings` giữ lại chỉ để đọc file cũ rồi bị migration làm rỗng.
8. `Profile`: `Kind` = toolId, `ActionId` = hậu tố (rỗng = chạy lệnh gốc), `Vals` như cũ. Loại `library` cũ được migrate thành `Kind=toolId, ActionId=""`; `custom` (lệnh riêng) giữ nguyên. `StackStep` tương tự.
9. **Khoá file khả năng giữ nguyên là toolId.** Preset được seed vào thư viện với `Id` = kind cũ (`dotnet`, `git`, `angular`, `npm`), nên file khả năng, profile, stack, task key cũ không phải đổi tên.
10. **Migration** (`WorkspaceMigration.Upgrade`, idempotent, sao lưu `workspaces.json.v{n}.bak` trước khi ghi): seed `ToolEntry` cho mỗi kind đang được bind, chuyển LibraryBindings → Bindings, remap profile/stack `library` → toolId. Chạy khi nạp workspace.
11. **UI**: mỗi `Binding` là một tab tool, cùng một trang: danh sách hậu tố/action, profile, nút "Khả năng…", sửa tool, gỡ. Bỏ `BuildLibraryPage` riêng. Dialog thêm tool vào workspace gồm: (a) chọn từ thư viện (hàng giống thẻ thư viện), (b) mục "Gợi ý từ thư mục này" (preset nhận diện được), (c) nút "Đăng ký tool mới…" mở đúng `ToolEditWindow`. `ToolEditWindow` thêm: Path tuỳ chọn khi có lệnh, mục nguồn hậu tố, nút "Khả năng…" cho mọi tool lệnh.

## Acceptance theo hành vi (đối chiếu ở P7)

- A1. Dữ liệu cũ (workspace có binding `angular`/`npm` + tool thư viện + profile `library`) mở lên không mất tab, profile, stack, bảng khả năng.
- A2. Đăng ký một tool bất kỳ (vd `python -m ai_autopilot`) từ dialog thêm tool của workspace, bằng đúng form như thư viện, rồi thấy tab của nó có nút "Khả năng…", quét hoặc nhập tay hậu tố, và tạo profile theo hậu tố đó.
- A3. Tool file chạy (exe) cũng gắn được, tạo được profile (chạy gốc + Args).
- A4. Không còn đoạn code nào rẽ nhánh "tool dựng sẵn vs tool thư viện" ở runner, editor, MCP, UI; chỉ `custom` (lệnh riêng) là nhánh riêng.
- A5. Không còn tên tool cụ thể (dotnet/git/angular/npm) trong code ngoài `ToolPresets` mặc định và test.
